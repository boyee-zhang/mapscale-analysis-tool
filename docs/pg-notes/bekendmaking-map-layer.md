# 建设许可上地图:`/bekendmakingen`,以及一次把自己骗了两轮的测量 (2026-10-29)

起点是一句话需求:「建设许可可以在地图上标注上吗,点击可以看到多久到多久的什么建筑许可情况」。
数据在 `a9a736a` 已经进库(54,566 条公告 / 88,877 条几何),这一轮是把它变成一个端点、
一个地图图层和一个按月统计面板。

真正值得记的不是端点,是**一个 31 倍的 plan cache 悬崖**,它一直埋在 `/pois` 下面,
只是从没有人在同一个进程里把同一条空间查询跑够六次。

---

## 1. 头条:prepared statement 第 6 次执行掉下 31 倍悬崖

### 现象

把 30 分钟驾车等时圈(1,241 个顶点,命中 54,414 条)通过 asyncpg 连续打 10 次:

```
asyncpg 默认 (statement_cache_size=100)
  call 1   2.709s      call 4   9.014s
  call 2   2.496s      call 5   3.053s
  call 3   2.429s      call 6 104.173s   <-- 悬崖
```

在 psql 里用 `PREPARE` / `EXECUTE` 独立复现,同一个台阶:

```
EXECUTE #1..#5   2.27 - 2.62 s
EXECUTE #6      77.53 s
```

两条路径都在**第 6 次**掉下去,所以这不是 asyncpg 的 bug,是 PostgreSQL 的 plan cache。

### 机制

PostgreSQL 对 prepared statement 的前 5 次执行用**自定义计划**(带着实参重新规划),
第 6 次开始评估「一个通用计划够不够好」。我们的空间查询把搜索形状当参数传:

```sql
ST_CollectionExtract(ST_MakeValid(ST_SetSRID(ST_GeomFromGeoJSON($5), 4326)), 3)
```

规划时 `$5` 是个不透明的 text,规划器**看不到这个多边形,也就拿不到它的 bounding box**,
对 `ST_Intersects` 的选择率只能按默认值猜。它据此定下的通用计划是为「平均形状」准备的,
对我们这种形状是灾难性的。

asyncpg **默认把每条查询都发成服务端 prepared statement 并缓存**
(`statement_cache_size=100`),所以这不是一个要刻意触发的边界情况 —— 它是一个长期运行的
后端进程的正常状态。

### 修法

`api/main/db.py` 建池时整池设置:

```python
server_settings={"plan_cache_mode": "force_custom_plan"}
```

验证:同一条宽查询连续 12 次,**1.73–2.28 s,没有台阶**(有一个 5.4 s 的抖动,
那是噪声,不是 50 倍的跳变)。

重新规划在这里大约 1 ms,而查询本身是几十到两千毫秒,所以这个取舍是一边倒的。

### 为什么设在池上而不是这条查询上

`/pois` 用**完全一样的方式**传等时圈多边形(`ST_GeomFromGeoJSON($1)`)。它有同样的暴露面,
只是从来没有人在一个进程里对同一个足够宽的形状跑够六次 —— 浏览器每次点击都换中心点,
参数一变,查询文本不变、缓存条目却是同一条,计数照样累加。所以这是一个**已经存在的**
潜在故障,不是新端点引入的。

> 可复述的一句话:**「HTTP 200 不代表答案对」的计划版本 —— 同一条 SQL、同一个参数、
> 同一个连接,第六次比前五次慢 31 倍,代码没有任何一行变化。**

## 2. 我在这一轮里把自己骗了两次

### 2.1 带着并发负载读数(重犯)

中间有一段时间,后台同时跑着两个 job(asyncpg 悬崖测试 + 一个 77 秒的
`EXPLAIN ANALYZE EXECUTE`),都打同一个 `shared_buffers=128MB` 的实例。我在那段时间里
量到端点 6.3 s 和 7.7 s,并且**据此做了设计决定**(把两条查询合并成一条,理由是「跑了两遍
空间扫描」)。

把后台清干净以后重测:

| 查询 | 干净读数 (3 次) |
|---|---|
| 10 分钟步行,建设许可 | 0.10 / 0.69 / 0.71 s |
| 30 分钟驾车,建设许可 | 1.73 / 1.82 / 2.50 s |
| 30 分钟驾车,全部类型 | 1.88 / 2.17 / 2.27 s |

**真实最坏情况约 2 秒,不是 7.7 秒。** 合并成一条查询本身仍然是对的(一次空间扫描而不是
两次,一次往返而不是两次),但我当时给出的理由是用污染数据算的。

ORS 那次的教训是「一次只变一个轴,对着一个已知良好的对照」。这次我**连对照都没有** ——
机器上有我自己放的两个负载,而我没有先问一句「现在谁在用这个库」。
`pg_stat_activity` 查一次是 0.2 秒的事。

### 2.2 先写结论再测量

我把 `matched AS (SELECT b.*, …)` 改成显式列名,并且**在量之前**就把注释写成
「facets 从 830 ms 降到 118 ms」。那个 118 ms 是我编的。

实测(最宽形状,各两次):

```
b.*          1007 ms / 896 ms
显式列名      879 ms / 902 ms
```

**没有差别。** 我的机制解释("`raw jsonb` 被拖进物化 CTE")听起来完全合理,而且 CTE 确实
被物化、确实溢出到 7,294 个 temp block、确实被扫了四遍 —— 但溢出量由**行数**决定,
不由行宽决定,`raw` 每行才几百字节。

列名保留了(它说明了契约),但注释改成了实话:这是一次失败的预测,不是一次生效的优化。

> 两件事合起来是同一条:**先量,再写;量之前先确认没有别人在用这台机器。**

## 3. 模式设计里真正做了决定的几处

### 3.1 `ST_Intersects`,不是 `/pois` 用的 `ST_Contains`

不是风格差异。`poi.geom` 永远是 POINT,这两个谓词在点上等价;
`bekendmaking_locatie.geom` 里 POINT 63,167 / POLYGON 13,745 / LINESTRING 11,937 /
MULTIPOLYGON 28。**一块地跨在等时圈边界上,人是走得到的**,`ST_Contains` 会把它丢掉。

### 3.2 `DISTINCT ON` 折叠扇出,并且在同一次索引扫描里取代表点

一条公告平均挂 2.5 个几何(**订正 2026-11-12:全国导入后实测 1.72** —— 160,477 条 `bekendmaking_locatie` 对应 93,123 条有几何的公告。2.5 是在下面这 10,342 条建设许可的规模下测的,语料扩到 94,183 后没有重测。`DISTINCT ON` 的必要性不变,只是均值变了),**10,342 条建设许可里有 9,213 条正好是「一个点 + 同一块地的
一个多边形」**。不折叠的话地图会在同一个地址上画两三个点 —— 和之前那次
`count(*)` 把 119 条公告数成 282 的扇出是同一个毛病。

代表点取自**与形状相交的那些几何**,不是公告的全部几何。这是故意的:如果一条许可的点在
等时圈外、而它的地块多边形伸了进来,标记应该落在真正够得着的那部分上。

顺带它把代表点的解析留在了同一次扫描里。先 `DISTINCT identifier`、再按 identifier
二次查表取代表点的写法实测 **414 ms**,对 **25 ms** —— 因为那会变成每条存活公告一次
bitmap scan(370 次循环,1,518 buffers,101 ms 纯 I/O)。

### 3.3 `stage`(申请 / 批准)是从标题**推**出来的,不是数据源给的

这是建设许可最有用的一维:申请是个计划,批准是个要盖起来的东西。SRU 记录里**没有这个字段**
(`raw` 只有 subject / jaargang / publisher / 几个时间戳),所以它是对 `title` 的关键词匹配,
并且在 SQL、API、前端常量、面板文案四个地方都标注了「derived from the title」。

实测覆盖率(全部 10,342 条建设许可):besluit 5,139 (49.9%)、aanvraag 5,128 (49.8%)、
ontwerp 18、overig 21 (0.2%)。

三个让它足够安全的细节:

- **先判 besluit 再判 aanvraag**:荷兰语标题写成 "Besluit op de aanvraag …",两个词都出现时
  它是决定。不过全量里只有 25 条两个词都有,所以这个优先级几乎是惰性的。
- **不锚定在 `^`**:锚定版本漏掉 147 条 (1.4%),**全部来自 Diemen** —— 它给每条标题加
  "Gemeente Diemen: " 前缀。一个只在一个市镇上失效的解析器,在只有阿姆斯特丹数据的时候
  是看不见的。
- 剩下的 `overig` 是**真歧义**不是解析缺口:光一个词的 "Omgevingsvergunning"、
  "Geen vergunning nodig - …"。

**它在查询里算,不存成列。** 下一个省的标题可能换一种写法,而一个存下来的列要先回填才能
发现这件事。

### 3.4 `by_activiteit` 的数字不相加

一条许可可以同时带 bouwen + ruimtelijke ordening(阿姆斯特丹市中心 284 条建设许可里,
12 条同时是 ruimtelijke ordening)。这是**逐项计数,不是一个划分** —— 画成柱状图对,
画成饼图错。SQL 注释和面板文案都写了这句。

### 3.5 没有做的:`doc_type` 反范式化

迁移 `0009` 把「`doc_type` 也复制到位置表」记成了一个**待决定**。这个功能让 doc_type
过滤变成了主过滤器,所以它比当时更值钱了 —— 现在的计划是扫**全国 10,306 条 bouwen 许可**
(6,751 buffers)再和本地 2,000 条命中做 hash join,代价随全国许可量涨,不随本地命中量涨。

还是没做。最坏情况 2 秒,而这是第二个复制列、同样的维护义务。记在这里当成一个
**待决定**,不是待发现。

## 4. 前端:两个值得记的

### 4.1 500 个点不走 DOM marker

`PoiMarker` 一个 POI 一个 DOM 节点,几十个没问题。这个端点上限 500 条,驾车等时圈**每次**
都顶满,所以走 GeoJSON source + circle layer:一个节点,MapLibre 自己做命中测试。

### 4.2 点击落在光晕上,不在点上

第一版只把小圆点注册成可点击层。浏览器里实测:**一次视觉上明确落在许可上的点击穿透到了
地图处理器,把中心点挪了、等时圈重算了、弹窗没出来。**

原因是点在不同缩放下只有 2–7 px,而它外面那圈半透明光晕是 4–18 px —— 人瞄的是光晕。
修法是把两层都注册成可点击,并且两层都进 `MapContainer` 的点击守卫。

附带一条 MapLibre 的坑:`e.originalEvent.stopPropagation()` **拦不住** MapLibre 自己的
分发,同一次点击照样会送到裸 `map.on('click')`。真正的守卫必须写在那个 handler 里,
用 `queryRenderedFeatures(e.point, { layers: [...] })` 判断。

> 这个 bug 读代码读不出来 —— 两层都在、颜色都对、handler 都注册了。只有在浏览器里
> 点一下才会发现瞄的和测的不是同一个东西。

## 5. 当前状态

- 端点 `GET /api/main/bekendmakingen`,`building_permits=true` 是建设许可的简写。
- 窗口默认往回 365 天,上限 730 天;`minutes` 上限 60。两个轴都有界,因为无界的那一头是
  54,414 条命中和 4.8 MB 纯标题。
- `total` / `months` 覆盖全部命中,`items` 上限 500,`truncated` 说明是否截断。
  **月度柱子不能从 `items` 反推** —— 截断的列表会漏报月份。
- 库里只有 Amsterdam + Diemen 的 2026 年数据。自建 ORS 覆盖北荷兰约 55 个市镇。
- 没有数据库时端点返回 `shape: "unavailable"` 而不是 `total: 0`。
  空列表和「我们没有数据源」对调用方长得一模一样,而只有一个是真的。
